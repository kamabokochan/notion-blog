# ルーティング


## layoutとtemplateの違い

- どちらも共通のUI要素の提供をメインとする
- layoutはネストすることが可能

| layout     | template |
| ---------- | -------- |
| 状態を保持したい場合 | 初期化したい場合 |


## ルートレイアウト

- 最上位レベルのレイアウト
- 全てのルートに適用される

## メタデータAPI

- layout.jsなどにmetadataを定義する

	```typescript
	import type { Metadata } from 'next'
	 
	export const metadata: Metadata = {
	  title: 'Next.js',
	}
	 
	export default function Page() {
	  return '...'
	}
	```


## usePathname

- クライアントフック
- 現在の URL のパス名を読み取ることができる

## ルート間を移動する方法

- <Link>
	- <a>タグの提供。
	- Next.js でルート間を移動するための主要かつ推奨される方法
	- prefetch
		- ユーザーがリンクをクリックする前にページを事前に取得（プリフェッチ）して、ページ遷移の速度を向上させるためのもの。これにより、ユーザーがリンクをクリックしたときにすぐにページが表示されるため、よりスムーズな体験を提供できる。
		- SSRするページでは適用されない
- useRouter
	- クライアントフック
	- Linkが推奨されるため、基本利用しない
- redirect関数
	- サーバーコンポーネントでリダイレクト処理する関数
- history API（クライアントのみ）
	- [**`window.history.pushState`**](https://nextjs.org/docs/app/building-your-application/routing/linking-and-navigating#windowhistorypushstate)
		- ブラウザの履歴スタックに新しいエントリを追加
	- [**`window.history.replaceState`**](https://nextjs.org/docs/app/building-your-application/routing/linking-and-navigating#windowhistoryreplacestate)
		- ブラウザの履歴スタックの現在のエントリを置き換え

## ルーターキャッシュ

- SSRでは機能しない
- クライアントサイドのページ遷移時にキャッシュをなるべく利用するもの

## エラー処理

- `error.js`
	- ルートでキャッチして処理する
	- ネストも可能。エラーは、`throw`することで最も近いエラーまでバブルアップする

## ローディング

- `loading.js`
	- 読み込み時のUIを提供する

## ルートグループ

- フォルダ名の先頭に`括弧()` をつける

	```typescript
	app/
	├── dashboard/
	│   ├── page.js
	│   ├── (admin)/
	│   │   ├── settings/
	│   │   │   └── page.js
	│   │   └── users/
	│   │       └── page.js
	│   └── (reports)/
	│       ├── sales/
	│       │   └── page.js
	│       └── analytics/
	│           └── page.js
	```

	- URLに反映せずにグルーピングができる。

## **並行ルート**

- 同じURLページ内に動的に複数のコンテンツを出し分ける機能を実装可能
	- `app/(user)/@profile` や `app/(user)/@settings` のように`@` を使って設定する

# データ取得


## サーバーコンポーネントでのFetch

- [https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#fetching-data-on-the-server-with-the-fetch-api](https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#fetching-data-on-the-server-with-the-fetch-api)
- Next15では、fetchはデフォルトではキャッシュしない

## クライアントコンポーネントでのFetch

- [https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#fetching-data-on-the-client](https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#fetching-data-on-the-client)
	- SWRなどのライブラリを利用可能

## リクエストのメモ化

- [https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#reusing-data-across-multiple-functions](https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#reusing-data-across-multiple-functions)
	- 同じURL、オプションで呼び出す場合には、リクエストを複数行っても1つになる

## 並列および順次データ取得

- [https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#parallel-and-sequential-data-fetching](https://nextjs.org/docs/app/building-your-application/data-fetching/fetching#parallel-and-sequential-data-fetching)
	- 順次データフェッチ（シーケンシャルデータフェッチ）
		- ネストされたコンポーネントがあり、各コンポーネントが独自のデータを取得する場合、それらのデータ要求が[メモ化されて](https://nextjs.org/docs/app/building-your-application/caching#request-memoization)いないと、データの取得は順番に行われる
		- フェッチが他のフェッチの結果に依存する場合に必要になる場合がある
	- 並列データフェッチ
		- 1つのコンポーネント内で並列にデータフェッチするパターン

## フォーム

- [https://nextjs.org/docs/app/building-your-application/data-fetching/server-actions-and-mutations#forms](https://nextjs.org/docs/app/building-your-application/data-fetching/server-actions-and-mutations#forms)
	- formのactionにサーバー関数を指定して、formDataを受け取る例

	```typescript
	export default function Page() {
	  async function createInvoice(formData: FormData) {
	    'use server'
	 
	    const rawFormData = {
	      customerId: formData.get('customerId'),
	      amount: formData.get('amount'),
	      status: formData.get('status'),
	    }
	 
	    // mutate data
	    // revalidate cache
	  }
	 
	  return <form action={createInvoice}>...</form>
	}
	```

	- formのフィールドが多い場合は、entriesなどの使用を検討
